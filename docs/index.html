Case 01 · Supplier master data · Fictional

Change the shipment.
Never the payment.

An accounts-payable specialist processes an approved shipping-address change while a separate, unauthorized bank-field request is attempted. Every step is bounded, executed, and checked by a second identity that cannot write.

Fictional dataBubblewrap-isolated browserNo payment actionsPoint-in-time evidence
In scope

The approved shipping address, on the exact supplier and record version.

Out of scope

Bank accounts, tax identifiers, unapproved values, any other supplier.

Proof, not promise

After the write, a separate read-only principal reads the portal back. Success is only shown when that read-back succeeds.

Approval binds to this hash. The contract is generated by a fixed template, not interpreted by a model, and approval is a local demo action rather than authenticated identity verification.

3 · Resolve matches

Matching changes no records. An ambiguous supplier is paused for a human; nothing is selected automatically. Selections expire in five minutes and invalidate if the record version changes.

Run timeline

What is enforced

  • 1Server-side capabilityTarget supplier, allowed field, approved value and record version are bound server-side, not in the model's hands.
  • 2Action filterRaw coordinates are resolved to whitelisted elements. Unknown or out-of-bounds actions stop the run before execution.
  • 3Isolated browserBubblewrap namespaces, no network, no workspace, no model key. Isolation is probed before any action.
  • 4Second identityA read-only principal reads the portal back over HTTP and compares value, version and restricted-field hashes.
